# CardCore product requirements document

## Product overview

CardCore is a source-only mainframe credit card management reference application. The repository contains COBOL programs, CICS resource definitions, BMS maps, VSAM data layouts, JCL, scheduler definitions, and optional IMS, DB2, and MQ extensions. The README identifies the application as a fork of AWS CardDemo, with credit card management workflows implemented in COBOL, CICS, VSAM, and JCL, and states that the repo is not expected to compile or run locally. Sources: `README.md:17-27`, `README.md:46`, `README.md:136-155`.

The product scope covers interactive CICS screens, backend batch jobs, scheduler-driven operations, and optional integration modules. Core CICS resources are defined in `app/csd/CARDDEMO.CSD:1-503`; optional authorization, DB2 transaction-type, and VSAM/MQ resources are defined in `app/app-authorization-ims-db2-mq/csd/CRDDEMO2.csd:1-79`, `app/app-transaction-type-db2/csd/CRDDEMOD.csd:1-60`, and `app/app-vsam-mq/csd/CRDDEMOM.csd:1-36`.

## Personas and access control

CardCore has two application roles in the shared COMMAREA: admin (`A`) and regular user (`U`). The user record stores user id, first name, last name, password, and user type. Sources: `app/cpy/COCOM01Y.cpy:25-28`, `app/cpy/CSUSR01Y.cpy:17-23`.

The sign-on workflow must authenticate against the `USRSEC` VSAM file, compare the entered password to `SEC-USR-PWD`, store `SEC-USR-TYPE` in the COMMAREA, and route admins to `COADM01C` while routing regular users to `COMEN01C`. Sources: `app/cbl/COSGN00C.cbl:209-236`.

The admin menu defines user list, user add, user update, user delete, transaction type list/update, and transaction type maintenance. These options are intended for admin users through sign-on routing. Sources: `app/cpy/COADM02Y.cpy:22-53`, `app/cbl/COADM01C.cbl:123-146`.

A permission constraint needs product confirmation: CICS resource definitions commonly show `RESSEC(NO)` and `CMDSEC(NO)`, so repository evidence points to application-level menu routing as the primary access control, not CICS resource security. Sources: `app/csd/CARDDEMO.CSD:306-488`.

## Data model overview

The core business entities are customer, account, card, card/account/customer cross-reference, transaction, transaction category balance, disclosure group, and user security. The CICS resource catalog registers the online VSAM resources for account, card, card alternate index, card cross-reference, customer, cross-reference alternate index, transaction, and user security files. Transaction category balance and disclosure group are batch-only VSAM files and are not registered in the CICS catalog. Sources: `app/csd/CARDDEMO.CSD:1-99`, `app/jcl/TCATBALF.jcl:20-61`, `app/jcl/DISCGRP.jcl:20-61`.

Customer records include customer id, name, address, phone, government identifiers, date of birth, EFT account id, primary card holder indicator, and FICO score. Account records include account id, active status, current balance, credit limits, open/expiration/reissue dates, current cycle credit/debit, ZIP, and account group. Card records include card number, account id, CVV, embossed name, expiration date, and active status. Sources: `app/cpy/CVCUS01Y.cpy:1-23`, `app/cpy/CVACT01Y.cpy:1-17`, `app/cpy/CVACT02Y.cpy:1-11`.

Transaction records include transaction id, type, category, source, description, amount, merchant details, card number, original timestamp, and processing timestamp. Transaction category balances aggregate account, type, category, and balance. Disclosure groups map account group, transaction type, and category to an interest rate. Sources: `app/cpy/CVTRA05Y.cpy:1-18`, `app/cpy/CVTRA01Y.cpy:1-10`, `app/cpy/CVTRA02Y.cpy:1-10`.

Optional modules add IMS pending authorization summary/detail data, DB2 fraud records, and DB2 transaction type reference tables. The authorization fraud table primary key is `(CARD_NUM, AUTH_TS)`. Transaction type categories have a foreign key to transaction type with delete restrict. Sources: `app/app-authorization-ims-db2-mq/README.md:252-330`, `app/app-authorization-ims-db2-mq/ddl/AUTHFRDS.ddl:1-28`, `app/app-transaction-type-db2/ddl/TRNTYPE.ddl:1-4`, `app/app-transaction-type-db2/ddl/TRNTYCAT.ddl:1-7`.

## Sign-on and menu requirements

Users must be able to sign on with a user id and password. The system must reject blank or invalid credentials, display the sign-on screen again, and place the cursor on the invalid field. Sources: `app/cbl/COSGN00C.cbl:116-157`, `app/cbl/COSGN00C.cbl:209-255`, `app/bms/COSGN00.bms:20-79`.

Regular users must see the main menu. Admin users must see the admin menu first and may navigate to admin functions. The main menu must reject invalid option numbers and block regular users from options marked admin-only in menu metadata. Sources: `app/cbl/COMEN01C.cbl:115-157`, `app/cpy/COMEN02Y.cpy:19-90`, `app/cbl/COADM01C.cbl:123-146`.

## Account and customer management requirements

Users must be able to view an account by account id and see account fields plus linked customer fields. Account id must be an 11-digit, nonzero numeric value. The view reads cross-reference, account, and customer data. Sources: `app/cbl/COACTVWC.cbl:306-313`, `app/cbl/COACTVWC.cbl:471-521`, `app/cbl/COACTVWC.cbl:628-679`, `app/cbl/COACTVWC.cbl:701-756`, `app/bms/COACTVW.bms:75-373`.

Users must be able to update account and customer information after fetching existing records. The update screen uses staged states for fetched details, changed values, confirmation, save completion, failure, and locking. Sources: `app/cbl/COACTUPC.cbl:652-849`, `app/cbl/COACTUPC.cbl:905-1003`, `app/bms/COACTUP.bms:75-507`.

The account update flow must validate yes/no indicators, dates, signed money fields, required address fields, SSN, date of birth, state/ZIP consistency, phone number components, EFT id, primary holder indicator, and FICO score. FICO must be within 300 through 850. Sources: `app/cbl/COACTUPC.cbl:1470-1675`, `app/cbl/COACTUPC.cbl:1783-2360`, `app/cbl/COACTUPC.cbl:845-849`.

When saving, the system must lock both account and customer records, compare the locked records against the originally fetched `ACUP-OLD-*` snapshot, and stop before rewriting if another update changed the data. Only after that optimistic-concurrency check passes may the system build the account and customer update records and rewrite `ACCTDAT` and `CUSTDAT`. Sources: `app/cbl/COACTUPC.cbl:3888-3952`, `app/cbl/COACTUPC.cbl:4109-4194`, `app/cbl/COACTUPC.cbl:3953-4103`.

## Card management requirements

Users must be able to list credit cards by account id and card number. Search values must be numeric when supplied; blank or zero values are treated as blank filters. The list flow reads card records from `CARDDAT`, applies account and card filters, supports paging, and returns messages for missing or invalid records. Sources: `app/bms/COCRDLI.bms:84-105`, `app/cbl/COCRDLIC.cbl:969-970`, `app/cbl/COCRDLIC.cbl:1003-1069`, `app/cbl/COCRDLIC.cbl:1123-1261`, `app/cbl/COCRDLIC.cbl:1382-1409`.

Users must be able to view card details by card number and, where applicable, account criteria. A supplied card id must be a 16-digit number. The system reads `CARDDAT` by card number or reads `CARDAIX` by account. Sources: `app/cbl/COCRDSLC.cbl:291-365`, `app/cbl/COCRDSLC.cbl:622-718`, `app/cbl/COCRDSLC.cbl:736-810`, `app/bms/COCRDSL.bms:75-152`.

Users must be able to update card information after fetching existing card data. The card update flow validates account id, card number, embossed name, active status, and expiration month/year, then confirms and rewrites the card record. Sources: `app/cbl/COCRDUPC.cbl:578-636`, `app/cbl/COCRDUPC.cbl:641-717`, `app/cbl/COCRDUPC.cbl:721-945`, `app/cbl/COCRDUPC.cbl:988-1001`, `app/cbl/COCRDUPC.cbl:1420-1521`, `app/bms/COCRDUP.bms:79-146`.

The CICS catalog defines a developer transaction `CDV1` for `COCRDSEC`, described as credit card search, but the matching COBOL source was not present in `app/cbl`. Sources: `app/csd/CARDDEMO.CSD:211-218`, `app/csd/CARDDEMO.CSD:388-398`.

## Transaction management requirements

Users must be able to list transactions 10 rows at a time, page forward/backward, and select a transaction for detail view. Sources: `app/cbl/COTRN00C.cbl:5-39`, `app/cbl/COTRN00C.cbl:149-210`, `app/cbl/COTRN00C.cbl:281-442`, `app/cbl/COTRN00C.cbl:591-695`, `app/bms/COTRN00.bms:75-458`.

Users must be able to view a transaction by transaction id. The system requires a nonblank transaction id, reads `TRANSACT`, and displays card, type, category, source, amount, description, timestamps, and merchant fields. Sources: `app/cbl/COTRN01C.cbl:149-190`, `app/cbl/COTRN01C.cbl:267-285`, `app/bms/COTRN01.bms:75-267`.

Users must be able to add a transaction using either account id or card number. The system resolves the account/card relationship through cross-reference files, requires transaction type, category, source, description, amount, original date, processing date, merchant id, merchant name, merchant city, and merchant ZIP, then confirms the add with `Y/N`. Sources: `app/cbl/COTRN02C.cbl:115-188`, `app/cbl/COTRN02C.cbl:193-320`, `app/bms/COTRN02.bms:75-302`.

Transaction add validation requires numeric type/category, amount format `-99999999.99`, dates in `YYYY-MM-DD`, and valid dates through `CSUTLDTC`. The system generates the next transaction id by reading the previous transaction and incrementing before writing `TRANSACT`. Sources: `app/cbl/COTRN02C.cbl:322-466`, `app/cbl/COTRN02C.cbl:576-749`.

The transaction add menu entry is currently user-accessible, although a nearby source comment indicates “Admin Only” was considered and commented out. Sources: `app/cpy/COMEN02Y.cpy:67-72`.

## Bill payment requirements

Users must be able to enter an account id, view current balance, and confirm an online bill payment. Sources: `app/cbl/COBIL00C.cbl:156-235`, `app/bms/COBIL00.bms:75-135`.

If the account balance is nonpositive, the system treats the account as having no payment due. When confirmed, the system creates a transaction with type `02`, category `2`, source `POS TERM`, description `BILL PAYMENT - ONLINE`, merchant id `999999999`, merchant name `BILL PAYMENT`, merchant city `N/A`, and amount equal to current account balance. The account balance is reduced by that transaction amount. Sources: `app/cbl/COBIL00C.cbl:198-235`.

The bill payment flow reads the account with update intent, reads account/card cross-reference data, writes the transaction, and rewrites the account. Sources: `app/cbl/COBIL00C.cbl:343-395`, `app/cbl/COBIL00C.cbl:406-539`.

## Batch reporting requirements

The batch report process backs up and sorts transaction data, filters process dates between supplied start/end dates, joins transaction type/category descriptions, groups by card/account, and writes report details and totals. Sources: `app/jcl/TRANREPT.jcl:23-80`, `app/proc/TRANREPT.prc:21-78`, `app/cbl/CBTRN03C.cbl:160-217`, `app/cbl/CBTRN03C.cbl:274-373`, `app/cbl/CBTRN03C.cbl:495-507`.

The statement job must create a transaction file keyed by card and transaction id, then produce text and HTML statements using transaction, xref, account, and customer data. Sources: `app/jcl/CREASTMT.JCL:19-96`, `app/cbl/CBSTM03A.CBL:2-9`, `app/cbl/CBSTM03A.CBL:322-502`, `app/cbl/CBSTM03A.CBL:675-721`, `app/cbl/CBSTM03B.CBL:2-8`, `app/cbl/CBSTM03B.CBL:125-226`.

## Daily posting requirements

The daily posting job must read daily transaction records, validate account and card references, update account balances, write accepted transactions to the transaction VSAM file, and write rejected transactions to a reject file. Sources: `app/jcl/POSTTRAN.jcl:19-46`, `app/cbl/CBTRN02C.cbl:160-231`, `app/cbl/CBTRN02C.cbl:390-579`.

The posting process must maintain transaction category balances. If a category-balance record does not exist, it must create one; if it exists, it must add the daily transaction amount and rewrite the record. Sources: `app/cbl/CBTRN02C.cbl:474-539`.

## Interest calculation requirements

The monthly interest job must run `CBACT04C` against transaction category balances, account data, account/card xref data, disclosure groups, and generated system transactions. Sources: `app/jcl/INTCALC.jcl:19-41`, `app/cbl/CBACT04C.cbl:181-224`.

For each account/category balance, the system reads the interest rate from the disclosure group using account group, transaction type, and category. If no matching disclosure group is found, it attempts the `DEFAULT` group. Sources: `app/cbl/CBACT04C.cbl:415-455`, `app/cpy/CVTRA02Y.cpy:1-10`.

The system computes monthly interest as `(TRAN-CAT-BAL * DIS-INT-RATE) / 1200`, writes a system transaction with type `01`, category `05`, source `System`, description `Int. for a/c <account>`, and adds total interest to account current balance. It resets current cycle credit and debit to zero. Fee calculation is defined as a stub. Sources: `app/cbl/CBACT04C.cbl:352-518`.

## Authorization and fraud requirements

The optional authorization module must process authorization requests through IMS, DB2, and MQ artifacts. Sources: `app/app-authorization-ims-db2-mq/README.md:36-86`, `app/app-authorization-ims-db2-mq/csd/CRDDEMO2.csd:1-79`.

Authorization must resolve card/account/customer data, calculate available credit, approve when funds and account/card checks pass, and decline when the card/account is missing, available credit is insufficient, or fraud/inactive conditions apply. Approved responses use code `00` and approved amount equal to requested amount; declined responses use response code `05` and approved amount zero. Sources: `app/app-authorization-ims-db2-mq/cbl/COPAUA0C.cbl:445-681`, `app/app-authorization-ims-db2-mq/cbl/COPAUA0C.cbl:685-728`.

The fraud inquiry screen must list fraud authorization records from DB2 by card number and timestamp, with fraud details stored in `CARDDEMO.AUTHFRDS`. Sources: `app/app-authorization-ims-db2-mq/cbl/COPAUS0C.cbl:261-355`, `app/app-authorization-ims-db2-mq/ddl/AUTHFRDS.ddl:1-28`.

## DB2 transaction type maintenance requirements

The optional transaction type module lets admins maintain transaction type reference data in DB2 and synchronize it back to VSAM-style files. Sources: `app/app-transaction-type-db2/README.md:6-143`.

Admins must be able to list transaction types with filters and paging, select one row, and request update or delete. Delete and update requests require confirmation. Sources: `app/app-transaction-type-db2/cbl/COTRTLIC.cbl:338-367`, `app/app-transaction-type-db2/cbl/COTRTLIC.cbl:792-860`, `app/app-transaction-type-db2/cbl/COTRTLIC.cbl:941-1050`.

Admins must be able to add, update, or delete a transaction type. The program validates transaction type code and description, reads existing DB2 rows, updates when present, inserts when not found, and deletes by type. Sources: `app/app-transaction-type-db2/cbl/COTRTUPC.cbl:758-1004`, `app/app-transaction-type-db2/cbl/COTRTUPC.cbl:1447-1664`.

Batch maintenance must accept input actions `A`, `U`, and `D`, with `A` meaning add, and apply them to `CARDDEMO.TRANSACTION_TYPE`. `COBTUPDT` also ignores input records whose action is `*`. Extract jobs unload `TRANSACTION_TYPE` and `TRANSACTION_TYPE_CATEGORY` data ordered by type/category. Sources: `app/app-transaction-type-db2/cbl/COBTUPDT.cbl:91-219`, `app/app-transaction-type-db2/jcl/MNTTRDB2.jcl:5-18`, `app/app-transaction-type-db2/jcl/TRANEXTR.jcl:51-115`.

## VSAM and MQ inquiry requirements

The optional VSAM/MQ module exposes backend CICS transactions for system date and account inquiry. Sources: `app/app-vsam-mq/README.md:6-138`, `app/app-vsam-mq/csd/CRDDEMOM.csd:1-36`.

The date inquiry transaction must read a request from MQ, call CICS `ASKTIME` and `FORMATTIME`, and reply with the system date while preserving message id and correlation id. Sources: `app/app-vsam-mq/cbl/CODATE01.cbl:283-401`.

The account inquiry transaction must read an MQ request, retrieve account details from `ACCTDAT`, and send the account response to the reply queue. Sources: `app/app-vsam-mq/cbl/COACCT01.cbl:181-214`, `app/app-vsam-mq/cbl/COACCT01.cbl:222-285`.

MQ open, get, put, and close failures must write an error message to `CARD.DEMO.ERROR`. Sources: `app/app-vsam-mq/cbl/CODATE01.cbl:405-521`, `app/app-vsam-mq/cbl/COACCT01.cbl:289-312`.

Confidence is high, 85 percent, for functional requirements that map directly to COBOL, BMS, JCL, DDL, and CSD artifacts in the repository.

Confidence is medium, 65 percent, for final access-control boundaries. The code defines admin/user roles and menu-based routing, but CICS resource definitions show application security may not be enforced at the CICS transaction level. Sources: `app/cpy/COCOM01Y.cpy:25-28`, `app/cbl/COSGN00C.cbl:209-236`, `app/csd/CARDDEMO.CSD:306-488`.

- Is the missing `COCRDSEC` source intentional, or should developer card search be excluded from product scope despite CSD registration in `app/csd/CARDDEMO.CSD:211-218` and `app/csd/CARDDEMO.CSD:388-398`?
- Should transaction type DB2 maintenance be considered optional admin scope only, or required scope for a target migration?

## Online transaction report request screen

Users must be able to request transaction reports from the online `CR00` screen. The screen offers Monthly, Yearly, and Custom date range report types, plus a `Y/N` confirmation field. Sources: `app/bms/CORPT00.bms:75-226`, `app/csd/CARDDEMO.CSD:137-140`, `app/csd/CARDDEMO.CSD:242-248`, `app/csd/CARDDEMO.CSD:409-418`.

Monthly reports must use the first through last day of the current month. Yearly reports must use January 1 through December 31 of the current year. Custom reports must require start and end month, day, and year fields, perform numeric and range checks, and validate both constructed dates through `CSUTLDTC`. Sources: `app/cbl/CORPT00C.cbl:212-255`, `app/cbl/CORPT00C.cbl:256-436`.

Before submission, the system must require confirmation. Blank confirmation prompts the user, `Y` or `y` submits, `N` or `n` clears and aborts, and any other value is rejected. On confirmed submission, the program writes an 80-column `TRNRPT00` JCL stream to the CICS transient data queue `JOBS`, executing `PROC=TRANREPT`. Sources: `app/cbl/CORPT00C.cbl:81-127`, `app/cbl/CORPT00C.cbl:462-535`.

The online report request does not read or write VSAM transaction records directly. It delegates report execution to batch JCL through `WRITEQ TD`; TDQ write failure displays “Unable to Write TDQ (JOBS)...”. Sources: `app/cbl/CORPT00C.cbl:517-535`.

## Fraud detail/toggle flow

Users must be able to view a selected pending authorization detail through `COPAUS1C` on transaction `CPVD`. The detail screen displays card number, authorization date/time, response, reason, amount, processing code, POS entry mode, source, MCC, card expiry, authorization type, transaction id, match status, fraud status, and merchant details. Sources: `app/app-authorization-ims-db2-mq/cbl/COPAUS1C.cbl:208-228`, `app/app-authorization-ims-db2-mq/cbl/COPAUS1C.cbl:291-357`, `app/app-authorization-ims-db2-mq/bms/COPAU01.bms:75-292`.

The detail flow must read the IMS pending authorization summary by account id and then read the selected detail segment by authorization key. PF8 must move to the next authorization detail for the account or display “Already at the last Authorization...”. ## Pending-authorization purge job

The optional authorization module must include batch job `CBPAUP0J`, which runs IMS BMP program `CBPAUP0C` with PSB `PSBPAUTB` to delete expired pending authorizations. The job supplies expiry days, checkpoint frequency, checkpoint display frequency, and debug flag through SYSIN. Sources: `app/app-authorization-ims-db2-mq/jcl/CBPAUP0J.jcl:20-38`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:98-108`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:183-210`.

The purge program must read each pending authorization summary with IMS `GN`, then read child pending authorization details with `GNP`. For each detail, it computes the authorization date from the inverted date key, compares it to the current Julian date, and qualifies the detail for deletion when the day difference is greater than or equal to the configured expiry days. Sources: `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:136-170`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:216-271`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:277-296`.

When an expired detail is deleted, the program must decrement approved counts and amounts for response code `00`; for all other response codes, it must decrement declined counts and amounts. It then deletes the detail segment with DLI `DLET`. Sources: `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:287-293`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:303-324`, `app/app-authorization-ims-db2-mq/cpy/CIPAUSMY.cpy:27-30`, `app/app-authorization-ims-db2-mq/cpy/CIPAUDTY.cpy:30-35`.

The current source contains a summary-delete defect that must be carried as a known bug or corrected in migration scope. After processing details, `CBPAUP0C` deletes the summary only when `PA-APPROVED-AUTH-CNT <= 0 AND PA-APPROVED-AUTH-CNT <= 0`, which checks the approved count twice and never checks `PA-DECLINED-AUTH-CNT`. The intended condition appears to be that both approved and declined counts are exhausted before deleting the summary. Sources: `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:156-158`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:328-347`.

The purge job participates in the CA7 daily flow after `CLOSEFIL` and before `POSTTRAN`. Summary read, detail read, detail delete, summary delete, and checkpoint failures display DIBSTAT context and abend with return code 16. Sources: `app/scheduler/CardDemo.ca7:42-70`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:223-241`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:255-271`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:303-347`, `app/app-authorization-ims-db2-mq/cbl/CBPAUP0C.cbl:352-383`.
